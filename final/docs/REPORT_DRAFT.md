## 본문 (2쪽 이내)

### 1. 자동화한 반복 업무
- 업무: 원화사에서 수정 PDF를 받으면 이전본과 비교해 변경 내용과 요청 반영 여부를 확인.
- 주체: 브랜드 매니저(본인). BM과 디자이너가 각각 수정 요청 → 수정 누락·예상 밖 변경·과거 내용 원복 위험.
- 빈도: 【월 __건 / 원화 1건당 평균 __회 수정】
- 기존 소요시간: 【1회 비교 평균 __분 (측정 방법: __)】

### 2. 설계 (n8n 백엔드 + 결과 전달)
- 흐름: 수정본 도착(로컬 after 폴더) → n8n Schedule이 로컬 API에 대기 건 조회 → 승인된 before/after 짝(pair_id) 비교 → 로컬 상세 보고서 생성 → 【결과 전달 방식: 안전 요약 메일 / B안 결과 메일】 → 발송 결과 기록.
- 왜 이렇게 설계했나
  - 실제 회사 원화는 외부 반출 승인이 확인되지 않아 **LOCAL_ONLY** 기본. Railway n8n은 PC 파일을 읽을 수 없으므로 PC의 n8n + 127.0.0.1 API 구조.
  - 숫자·문구 비교는 **코드가 결정적으로** 수행(외부 LLM 미사용). 아웃라인 원화 대응을 위해 렌더링 기반 시각 비교 추가.
  - 세트/단품 교차 매칭 금지, 파일명은 후보만 → **사람이 짝 확정**(manifest + 내용 해시).
  - 요청서가 없으면 '무엇이 바뀌었나'만 보고, 반영/누락 판정은 요청서가 있을 때만.
- 사람의 역할: 짝 확정, page_map 확인, 시각 후보의 실제 변경 여부 판단, 요청 충돌 결정, 인쇄 항목(색상·별색·바코드) 확인, 최종 승인.

### 3. 실행 결과
- 자동 실행: 【__회 (n8n Executions 캡처, 부록 A)】 — 수동 실행 제외
- 결과물 3건: 【pair_id / 상태 / 변경 건수 — 부록 B】
- 결과 전달: 【메일 수신 __건 (부록 C)】
- 정확도 관찰: 【실제로 잡은 변경 __건 / 놓친 변경 __건 / 오탐 __건 (사람 대조 기준)】

### 4. 원가와 효과
- 운영 LLM: 미호출(토큰 0). 서버/PC 비용: 【__ (가정/실측 구분)】. 개발 중 AI 사용량은 운영 원가와 별도: 【__】
- 시간: 기존 【__분】 → 자동화 후 사람 확인 【__분】 (측정 __건 기준, 가정 여부 표기)

### 5. 한계와 다음 단계
- 텍스트 레이어 밖 문자는 시각 후보만(OCR 미사용), 색상·별색·도련·바코드 품질 미검사, 임계값은 【실제 자료 검증 전/후】.
- 실데이터 반출·수업 제출 범위는 회사 확인 대상. 【확인 결과】
